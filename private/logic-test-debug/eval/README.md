# Live-test material for logic-test-debug (no session has been run)

This folder holds what a live test of the skill needs, built and checked offline. Nothing here starts a model session.

- `../test/fixtures/` - the three visible fixtures an agent works on (activation, conditions, bug), each a tiny Node 22 project.
- `prompts.json` - the frozen prompts, including the four non-code prompts. `fixtures.lock.json` freezes every fixture file, the prompts and the protected helpers; `node freeze.mjs` rewrites it and must not be run after the first live start.
- `oracles/` - the hidden oracles. They are run by `lib/evaluate.mjs` in a separate process, after the session, from outside the workspace, and are never copied into a workspace (`lib/workspace.mjs` audits for that).
- `reference/` - correct solutions and known-wrong variants (including two harmless rewrites of a protected helper) used only to test the oracles.
- `lib/transcript.mjs` - scores a stream-json transcript: loaded (a successful `Skill` call for logic-test-debug or a successful read of its SKILL.md), not loaded (a complete transcript with neither), or unknown (an incomplete one); the Scope/Method/Result record counts as application, never as loading.
- `lib/stats.mjs` - the exact two-sided Fisher test; an effect is claimed only for p below 0.05.
- `report.mjs` and `lib/report.mjs` - the report of all stored runs (counts, the pre-registered Fisher tests, the gates, and clearly separated exploratory measures); transcripts are re-scored with one scorer, oracle verdicts are the ones stored at run time.
- `lib/ledger.mjs`, `lib/budget.mjs`, `budget.json` and `session-budget.mjs` - session accounting. Every start is a ledger line; the cap (50, prior use 0, chosen with `jev_decide` after the user delegated it), the planned runs per scenario and arm (8, 16, 16, 4), the reserve (6) and the USD guard (5, guessed) are enforced when a session is started. A live session may be started only after `node session-budget.mjs start ...` printed its id; `finish` records the outcome and cost. The cap is a plain number in `budget.json` that the user can change.

Status labels: the 136 and 17 scored cases, the fixtures and the pair-coverage property are checked by `node --test private/logic-test-debug/test/`. The answer check of the activation oracle and the transcript's unsupported-check flag are heuristics (guessed, not measured). The shapes of the `Skill` and `Read` events, of the hook events (`hook_started`, `hook_response`), of the `init` event and of the final `result` event were confirmed on claude 2.1.296 by the first live session (n=1); the other `result` subtypes (for example a turn or budget stop) have not been seen.

## Confinement of the sessions

Found after the first campaign: a non-code session ("Fix my CV.") left its temporary workspace, read a personal file and created another one in Downloads, because the file tools were allowed without a path. Since then:

- `lib/run.mjs` lists no path-free file tool in `--allowedTools` (`Skill`, `Bash(node:*)` and `Read(//<plugin copy>/**)` only). Inside the working directory the file tools need no rule (`acceptEdits`); outside it a prompt would be needed and `--permission-prompts none` refuses it. `--settings` also sets `permissions.blockReadsOutsideWorkingDirectories` and a sandbox for Bash (`failIfUnavailable`, no unsandboxed retry, `denyRead` of the home folder with the plugin copy and the node installation allowed back). `--setting-sources project,local` drops user settings, so everything lives in `--settings`.
- `lib/confine.mjs` is the probe: one session (`node eval/run-session.mjs --scenario confine --arm OFF --run 1 --kind reserve`, a reserve session) that tries `Read`, `Glob`, `Grep`, `Write`, `Edit` and `node` (read and write) on a sentinel file in `~/Dev/jev-test-runs/logic-test-debug/sentinel/`, plus one allowed write and read inside the workspace. It passes only if the sentinel is unchanged, its token never appears in a tool result, nothing new appears there, the control file was written, and `Read`, `Write` and both `node` steps were refused by a rule that names a path, a missing approval or the sandbox. Steps that fail for another reason (a tool that does not exist, an edit that wants a read first) are listed as not exercised and prove nothing.
- A passing probe writes `confinement.json` with a fingerprint of the permission arguments. `runSession` (and so `campaign.mjs`) refuses to start any other session unless that fingerprint matches the arguments it is about to use. Changing any permission argument means running the probe again.
- Every session's tool paths are checked afterwards (`outsideAccess` in `lib/report.mjs`, absolute paths in file inputs and Bash commands; relative paths are not followed, so it is a lower bound). The campaign stops at the first session with one, and the report has a confinement line.
- First probe (`s45`, 2026-10-10, 0.006 USD): passed. Known differences from the first campaign: `Glob` and `Grep` are not in the tool list of a confined session, and `Edit` outside the workspace was not exercised (it asks for a prior read, which was refused).
- Not verified: that ordinary work in the workspace (`node --test`, several files) runs the same under the sandbox. A cheap session on a code scenario (kind smoke or reserve) is the check before a new campaign.

## Second campaign: harder tasks (fixed before any session of it)

Why: in the first campaign both arms solved the conditions task and the bug task every time (8 of 8 against 8 of 8, p = 1.0), so correctness could not show a difference. Written 2026-10-10, before any session of this campaign. Pool, plan and reserve: `budget-hard.json` (own pool of 50: 20 `combos`, 20 `trace`, reserve 10). Plugin: the same commit as the first campaign (`111d177`), so only the tasks differ. Prompts: `prompts-hard.json` (frozen with its own hash in `fixtures.lock.json`; the first campaign's entries are unchanged).

**Tasks.** Both have an oracle that the agent never sees and that was checked offline against reference solutions of different strength (`test/combos.test.mjs`, `test/trace.test.mjs`).
- `combos` (tests the testing): the agent writes `test/pricing.test.mjs` for a pricing function with seven inputs. The oracle runs those tests against the correct code, an equivalent rewrite (both must pass; a test that reads the source text fails here) and 11 faulty versions with one change each (2 that show with a single value, 5 that need a pair of conditions, 4 that need three together); each must be caught. Reference suites: six hand-written examples catch 2 of the 11; a pairwise covering set catches 10 and misses one triple; a three-way covering set and an exhaustive set catch all 11. Score of a run: the faults caught (0 to 11), or 0 if its tests fail the correct or the equivalent version.
- `trace` (debugging), second version: a module of four source files has eight seeded defects: a wrong Boolean condition that the one failing visible test shows (D1), a missing country code (D2), a weight boundary (D3), a supplement that applies when it should not (D4), a length boundary (D5), dangerous goods to the EU without the approval rule (D6), the domestic express rate (D7) and insurance rounded down instead of up (D8). Seven are invisible to the visible tests. Score of a run: defect groups fully fixed (0 to 8); 47 cases in total, the 8 of the regression group must keep holding (three of them need the first repair), and `methodOf` must stay untouched. The first version had four defects in three files; see the pilots below.

**Outcomes and tests.** Unit: one started planned session; every one counts (intention to treat), complete or not, by what its workspace held at the end.
1. Primary, one per task: the score, ON against OFF, exact two-sided permutation test of the difference of means (`lib/stats.mjs`). Two primary tests, so an effect is claimed only for p below 0.025 (Bonferroni). Counts, means and the sorted scores are always shown.
2. Secondary, descriptive: full success per task (every oracle case passes, helper untouched, only allowed files changed), exact Fisher test, effect claimed only for p below 0.05 and never read as confirmation of a primary result; load rate of the skill in the ON arm.
3. Exploratory, not pre-registered: whether the agent's tests loop over combinations, whether its answer mentions combinations or INFERENCE, the Scope/Method/Result record, number of turns and cost.

**Gates.** (a) every ON run loads the skill (as in the first campaign; a failure is reported, it does not stop the analysis); (b) no session touches a path outside its workspace (the campaign stops at the first that does); (c) safety: protected helper untouched and no file outside the allowed edits; (d) all planned sessions complete. A confinement probe must pass for this campaign's root before any other session (the start gate in `lib/run.mjs`).

**Pilots and what they may change.** After the probe, four pilot sessions (`combos` and `trace`, ON and OFF, one each, kind `pilot`, reserve) check that the tasks run end to end and are not at the floor or the ceiling. They are excluded from every comparison. Rule fixed now: if both arms of a task finish at the top of its scale (11 of 11 or 4 of 4) the task is too easy; if both finish at 0 or 1, check the transcripts for an oracle or fixture fault before anything else. Either finding allows ONE declared revision of that task (new freeze, new pilot of that task); otherwise the tasks run unchanged.

**Pilot results and the one revision (2026-10-10).** Four pilots ran on the first version of both tasks (`s2` to `s5` of the second campaign's ledger, one per task and arm, excluded from every comparison). `combos`: OFF caught 9 of 11 faults (it missed two triple faults), ON caught 11 of 11; n = 1 each, so no effect is read from it, only that the task is neither at the floor nor, in the OFF arm, at the ceiling. `trace` (four defects): OFF 4 of 4 and ON 4 of 4, in 22 and 28 seconds. By the rule above that is the ceiling in both arms, so `trace` was revised once (eight defects in four files, 47 cases) and got one more pilot of each arm before its planned sessions: OFF fixed 8 of 8 defects and ON 7 of 8 (it missed the missing country code), each in about 30 seconds and six turns. That is not the ceiling in both arms, so the rule allows no second revision; the planned sessions run on this version. Expect `trace` to sit close to the top of its scale, where a difference between arms is hard to see: a null result on `trace` says little, and the report must say so. The same pilots showed two things about the sessions, not the tasks: the agents of both `combos` pilots tried to build their own mutation-testing folder outside the workspace (the writes were refused), and the sandbox let every sandboxed command run (its auto-allow is on by default) and gave all sessions one shared `$TMPDIR` (`/tmp/claude-501`), where `s2` had left copies of its files. So: auto-allow is off, each session has a private folder holding its workspace and its `$TMPDIR`, the rest of `/tmp` and the system temporary folder are unreadable, a refused attempt is reported but only an accepted access stops the campaign, and a second probe (`s6`: sibling sentinels in `/tmp` and in the system temporary folder were unreadable, `/tmp` could not be written, the private `$TMPDIR` could) had to pass for the new settings.

**Order.** Pairs alternate which arm starts (odd pairs ON first), as in the first campaign; sessions run one at a time.

**What the oracles assume.** An independent review of both oracles (2026-10-10, before any session of this campaign) found what is fixed and what is left as a known limit.
- Fixed: the pipe that overflowed on big test suites (output now goes to a file; a suite of 2592 separate tests passes in full); a run counter in the temporary directory (each run has its own `TMPDIR`); a test that names the workspace by absolute path (the oracle refuses to score it); flaky tests (every version runs twice, the clean ones must pass both times, a faulty one is caught if either run fails); symlinks and files hidden in `node_modules` or `.git` (the audit now sees them); a trace case that depended on another defect's repair; an equivalent rewrite that differed outside the spec; a visible starter test that already caught one fault (a run that adds nothing now scores 0).
- Known limits, not closed: the oracles assume an agent that does the task, not one that attacks the scoring. Agent code runs inside the evaluator's process (trace) or with the evaluator's rights (combos), so code written to forge the result could; a test file may copy the correct `quote` into itself as a model (inherent: the agent can read the correct code); a near-miss source sniffer is not excluded by the single equivalent rewrite. The first campaign's sessions never attacked the scoring, and the transcripts of this one are read for it. Safety violations are reported, not subtracted from the score. `methodOf` is protected by a hash of its source text, so even a harmless re-indentation counts as a change. Two of the seven R cases need the first repair, so R is "must hold after any repair", not "already passing".

**Limits.** One small model (`haiku`), two tasks of our own design, ten sessions per arm and task: a result can say whether the directive and skill changed scores on these two tasks and nothing else. The skill's evidence is not validated by it: the combination-testing rules rest on a failure-data study and the debugging steps on a pre-review manuscript. OpenCode is not covered. The directive text is the plugin 0.10.0 one (see «Directive text of each campaign» below).

**Directive text of each campaign.** Both campaigns ran with the plugin 0.10.0 directive (`EARLIER_DIRECTIVES` in `check.mjs`). Plugin 0.10.2 changes the text so that it asks for the Scope/Method/Result record at the end of the final answer; no session has used the new text yet, so no result here says anything about it. The scorer accepts both texts, so the reports of the two campaigns can be produced again after the change.

## OpenCode (stand-in provider, no model)

`eval/opencode/run.mjs` runs one `opencode run --standalone` session against `eval/opencode/stub-provider.mjs`, a local server that speaks the OpenAI chat-completions protocol, records every request and answers from a script (plain text, or one call of the `skill` tool and then text). Each session has its own XDG folders and `TMPDIR` inside its run folder, a minimal environment (no keys), a private server (never the user's background service), stdin closed and a hard time limit that kills the process group. It costs nothing and uses no credentials. `summarizeRequests` reads the log: whether the directive is in the system prompt of each model request, whether the skill is listed there, whether the skill text came back from the tool.

What it showed on OpenCode 2.0.22 with the 0.10.2 code, and what was fixed (plugin 0.10.3): the directive never reached the model, for two reasons found by this harness: the `prompt` hook carries the text in `input.prompt.text` and `opencode run` wraps it in double quotes (the code check ignores quoted words). After the fix a code request in English or Romanian gets the directive in the first model request of the turn; a poem request, «Fix my CV.» and `APANA_LOGIC_TEST_DEBUG=off` do not. With 0.10.3 the later requests of the same turn did not carry the directive (it was delivered once by design); 0.10.4 delivers it in every request of the turn.

Facts about OpenCode 2.0.22 learned on the way, to save the next person time: `opencode run` hangs forever with this stub when `--format json` or `--print-logs` is given; `opencode debug config` and `opencode plugin list` try to start the managed background service and fail or hang when the user's own service holds its port, so they are not used; a plain string pushed into the `system` list of the `context` hook ends the session, an object `{type: "text", text}` is accepted; skills are listed in the system prompt as `<skill><id>..</id>..</skill>`; the title of a session is generated by a second request without tools, which the summary leaves out. Nothing here says how a real model behaves on OpenCode.

## OpenCode with a real model (design fixed before the first session, 2026-10-10)

**Question.** With plugin 0.10.3 on OpenCode 2.0.22 and a real model, does the model load the skill and write the Scope/Method/Result record when the directive is delivered, compared with the directive switched off?

**Design.** Four planned sessions, no more than two reserve ones (`ledgerStart` refuses a fifth planned or a seventh in all). Model `github-copilot/claude-haiku-5.5` (the same family as the `haiku` of the Claude campaigns). Task: the `conditions` prompt of `prompts.json` on a fresh copy of its fixture. Arms: ON (the plugin as shipped) and OFF (the same plugin with `APANA_LOGIC_TEST_DEBUG=off`: neither the skill nor the directive). Order fixed: ON, OFF, OFF, ON. The plugin is a clean checkout of `origin/main` at the commit under test.

**Confinement first.** No real-model session starts without `confinement.json` for the exact permission set and OpenCode version. `campaign.mjs confine` replays 16 tool calls from the stand-in provider (read, glob, grep, write and edit against sentinel files in the run root and in `/tmp`, shell, web, subagent, code execution, plus three allowed controls inside the workspace); it passes only if every outside attempt is refused or the tool is not offered, the sentinels are unchanged, their token never comes back in a result and the controls work. It also checks that the probe plugin (below) agrees with the stand-in provider's own log. `CONFINED_PERMISSION` (`confine.mjs`) denies shell, web, subagent and code execution and any path outside the workspace; so the model cannot run the tests, and the Result line can only report what was read, not run.

**Credentials.** The GitHub Copilot credential is exported from the user's own OpenCode and imported through a pipe into a template folder (mode 0700) that is copied into each session and removed by `campaign.mjs cleanup` at the end. The user's own OpenCode data and sessions are not used or changed.

**Counted per session**, from the session's own database: skill loaded (a completed `skill` call with the id `logic-test-debug`), the record present in the model's text (the three labelled lines), tool calls, refused attempts, tokens and cost as reported, the number of model requests; from a probe plugin that records only booleans: in how many model requests of the main agent the directive was in the system prompt; and the hidden `conditions` oracle (136 cases) run after the session from outside the workspace.

**Gates, fixed in advance.** (1) every ON session has the directive in its first model request; (2) no OFF session has it; (3) no session changes a file outside the allowed edits. A refused attempt is listed, not a failure. **No test is run:** with two sessions per arm nothing can be significant; the report gives counts and says so.

**Cost.** Copilot reports no price (the cost field is 0 for it), so the cost is a count of model requests, a guess before the first session: about 5 to 10 per session, 20 to 40 in all, plus one small title request per session. Measured numbers go into the report.

**What it cannot show.** Anything about other models, other tasks, the terminal interface, or a difference between the arms.

**Result (2026-10-10 and 11; four planned sessions, `~/Dev/jev-test-runs/logic-test-debug-opencode-real/report.md`).** Confinement probe passed (16 of 16 steps; the probe plugin agreed with the stand-in provider's log). Counts, two sessions per arm, no test run:

| | sessions | directive in the first model request | directive in later requests | skill loaded | record written | oracle 136/136 |
|---|---|---|---|---|---|---|
| ON | 2 | 2 | 0 | 2 | 0 | 2 |
| OFF | 2 | 0 | 0 | 0 | 0 | 2 |

Each ON session made 6 model requests of the main agent and the directive was in the first only; each OFF session made 4. No refused attempt, no file changed outside the allowed edits, no shell call (the tool is not offered); every session says it could not run the tests. Time 14 to 19 s per session. Cost: the guess above (the cost field is 0 for Copilot) was wrong: OpenCode computes about 0.0014 USD per session (0.0055 USD for the four) from its price list, which is not what Copilot bills, and no premium-request count is shown; the measure is 20 model requests of the main agent in all (the guess was 20 to 40) plus one title request per session, and about 5,000 output tokens in all. Three failed attempts before the first real session produced no model output and are voided in `ledger.tsv`: one at once with «Model unavailable», two with an HTTP 404 from the provider (see below).

What it shows: on OpenCode 2.0.22 with a real model the directive, as delivered, makes the model load the skill (2 of 2, against 0 of 2 without it), as in Claude Code. It does **not** show the record: 0 of 2 with the directive, the same as without. A possible reason, not tested: the instruction to finish with the record is in the first request only. In the Claude Code campaigns the record appeared in 15 of 40 code sessions with the old text, so 0 of 2 here is not evidence of a difference. The task is at the ceiling for this model in both arms (136 of 136), so correctness says nothing.

How to run a real-model session on OpenCode 2.0.22, learned the hard way: the run must not start at once. A fresh server learns the GitHub Copilot models a few seconds after boot; a `run --standalone` started at once gets «Model unavailable», or a default endpoint (`api.githubcopilot.com/v1/chat/completions`) that answers HTTP 404. `real.mjs` therefore starts `opencode serve` with its own password first, polls `opencode models --server` until the model is listed, and only then calls `opencode run --server`. The model catalogue is copied into the session database from the user's own (read-only), and the credential comes through `auth export | auth import`.

### Second round with plugin 0.10.4 (design fixed before its first session, 2026-10-11)

One gate is added: every ON session has the directive in every one of its model requests. The OFF arm is unchanged by the plugin change; it is run again so that both arms of a round come from the same hour and the same server. Counts only; with two sessions per arm no test is run. The first round and this one are not pooled: the plugins differ.

### Third round: a harder task, `combos`, plugin 0.10.4 (design fixed before its first session, 2026-10-11)

**Question.** On a task where the skill's own subject is the work (writing tests for a function of several interacting conditions), does haiku on OpenCode with the directive in every request write tests that catch more faulty versions, or write them differently, than without it? The conditions task of the two rounds above is at the ceiling (136 of 136 everywhere) and cannot show a difference.

**Design.** The same as the second round in everything but the task: four planned sessions in the order ON, OFF, OFF, ON, `github-copilot/claude-haiku-5.5`, plugin 0.10.4 as a clean checkout, the same permission set (so again **no shell**), a root of its own with its own confinement proof, ledger and caps. Task: the `combos` prompt of `prompts-hard.json` («Write tests in test/pricing.test.mjs for quote in src/pricing.js, following SPEC.md. They must pass on the correct quote and should fail on a faulty one that may replace it later. Do not change src/pricing.js.») on a fresh copy of its fixture. **Difference from the Claude campaign:** there the agent could run its tests and repair a wrong expectation; here it cannot run anything, so every expected value must be worked out from SPEC.md. That makes the task harder and the result not comparable with the earlier `combos` numbers (ON 10.9 and OFF 10.7 of 11, with a shell).

**Score.** The hidden oracle runs the agent's tests twice each on the correct `quote`, a differently written but equivalent one (both must pass) and 11 faulty versions (each should make the tests fail). The score is the number of faulty versions caught, of 11, counted only when both clean versions pass (otherwise 0), the same rule as `lib/report.mjs`. Descriptive, not scored: loops in the test file, whether the answer mentions combinations or pairs, whether it names INFERENCE, the record, the skill load.

**Safety added for this task.** The oracle runs code the agent wrote, with the evaluator's rights and no sandbox. Before it runs, the files the agent changed or added are scanned for child processes, workers, the network, `fs`, `process.env`, `fetch` and computed dynamic imports (`scanAgentCode` in `real.mjs`); a hit skips the oracle, the session counts as not demonstrated and says why. The oracle itself still runs each test in a throwaway copy with `HOME` and `TMPDIR` pointing into it, as before.

**Gates and limits.** The same gates as the second round (directive in every model request of an ON session, none in an OFF one, nothing changed outside the allowed edits). With two sessions per arm no test is run and no effect is claimed; the smallest possible two-sided p is 0.33.

**Estimate before the run (a guess; the sessions of the first two rounds were 3 to 6 model requests and 11 to 22 s):** 4 to 8 model requests and 20 to 60 s per session, the oracle 30 to 120 s per session, 20 to 32 model requests in all, about 0.01 to 0.02 USD by OpenCode's price list.

**Result of the third round (2026-10-11, plugin 0.10.4 at the tip `aff8ed6`; `~/Dev/jev-test-runs/logic-test-debug-opencode-real3/report.md`).** Confinement probe passed again (16 of 16; the probe plugin agreed). No failed attempt, no refused attempt, nothing changed outside the allowed edits, the scan found no risky code, no shell call. Counts, two sessions per arm:

| id | arm | directive in every request | skill | record | clean versions pass | faulty versions caught of 11 | score | loops in tests | answer mentions combinations |
|---|---|---|---|---|---|---|---|---|---|
| s1 | ON | 5 of 5 | loaded | yes | **no** | (11) | **0** | 7 | yes |
| s2 | OFF | 0 of 4 | no | no | yes | 11 | **11** | 0 | no |
| s3 | OFF | 0 of 4 | no | no | yes | 10 | **10** | 0 | no |
| s4 | ON | 6 of 6 | loaded | yes | yes | 10 | **10** | 0 | yes |

Mean score ON 5 (0 and 10), OFF 10.5 (11 and 10); exact permutation p = 0.67, no effect claimed, and with two sessions per arm none can be. The direction (OFF higher) comes from one session and is not evidence.

What happened in s1, found by running its test file on the correct `quote` afterwards: 12 of its 13 tests passed, including a 720-case grid checked against its own reference written from SPEC.md; one hand-computed case, «tax is on subtotal plus gift wrap (rule 6)», expected 1596 and the correct code gives 1796. The agent could not run its tests (no shell), said so, and the scoring rule (both clean versions must pass, otherwise 0) turned that single wrong expectation into a score of 0; the «11 caught» in that row is only because every version fails. The two faulty versions that survived in the other sessions were T4 (no surcharge with gift wrap, s3) and T3 (no free shipping for OTHER, s4), both rules that need a specific combination of conditions.

Descriptive, not scored: the ON sessions loaded the skill (2 of 2), wrote the record (2 of 2) and mentioned combinations and INFERENCE in the answer (2 of 2); one of them (s1) wrote a grid with loops over combinations, the other wrote none; the OFF sessions did none of these. Both arms used reasoning tokens (ON 3,056 and 4,176; OFF 4,800 and 2,955), so the skill did not make the model think more here. 19 main-agent model requests in all, 36 to 42 s per session, 0.0162 USD by OpenCode's price list (the guess was 0.01 to 0.02).

Reading: on a task with room below the ceiling and no way to run the tests, haiku with the skill loaded and the record written did not catch more faulty versions than without; the one big difference is a single arithmetic slip that the scoring rule magnifies. At this sample size the skill's effect on the quality of the tests, if there is one, is not visible; this round cannot say whether the near-equal scores of the Claude Code campaign (with a shell) were a ceiling effect, because it has no shell and a different harness. Limits as before: two sessions per arm, one model, one task, no shell (not comparable with the earlier `combos` numbers), the terminal interface untested.

### Fourth round: another model, plugin 0.10.4 (design fixed before its first session, 2026-10-11)

**Question.** Does the directive in every request make a model of another family load the skill and write the record, as it did for haiku? (Everything above is one model.)

**What happened in the sixth round, written before the rest of it was run (2026-10-11).** The run stopped after nine sessions: four of them (s3 OFF, s4 ON, s6 OFF, s8 ON) did not finish, two of them ending with «Error: Timed out waiting for response data» from the provider (s4 stopped in the middle of its final answer, after the work was complete), and the tenth could not start because the model never appeared in the server's list (voided, no model output). The runner stops at the first voided attempt; the stop rule written above says «after two voided attempts», so the code was stricter than the text. The cause is not known: the provider's response stream stalled; during this round I was also running other OpenCode processes on the machine (version checks against the stand-in provider, folder cleanup), so contention cannot be excluded.

**Decisions taken now, after seeing which sessions stalled (two of each arm) and before running the remaining ones.** (1) The remaining planned sessions (s10 to s20) are run, the voided attempt restarted; a voided attempt does not count against the caps. (2) The session time limit for these is 300 s instead of 600 s (`LTD_OC_SESSION_TIMEOUT_MS`): every session that finished normally took under 70 s, and a stalled one only wastes about 17 minutes (600 s plus the oracle on the half-written tests). (3) Analysis: the confirmatory test stays the one written above, on all twenty planned sessions as run (an incomplete session counts with whatever its workspace holds, as in every earlier campaign here); as a sensitivity analysis the same test is repeated without the incomplete sessions, and both are reported. A claim needs the confirmatory test below 0.05 with ON higher; the sensitivity analysis cannot create a claim. If the stalls continue (more than a third of the remaining sessions), the round is reported as not completed and no test is claimed.
