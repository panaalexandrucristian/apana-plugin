# omlx

oMLX serves MLX models behind OpenAI/Anthropic-compatible APIs with continuous batching, a tiered (RAM + SSD) KV cache, a memory guard, a built-in web chat and, for MoE models, expert offload to SSD. This skill gets a model running on this Mac and picks its settings from the machine and the model instead of from guesses. Answer in the user's language. Run the scripts as `python3 -I ${CLAUDE_SKILL_DIR}/scripts/<name>.py`. `allowed-tools` pre-approves only these four scripts; `curl`, `open`, `pbcopy` and `ps` go through the normal permission prompt.

## Run a model (the flow)

Do these in order. The user asking to run a model is the consent for steps 2 to 6; stop and ask only where a step says so.

1. **Look first.** `omlx_ctl.py status` prints JSON: `installed`, `version`, `server` (the result of probing port 8000 with and without the skill's key, not proof of who owns the process: `down`; `ours` = accepts the key; `needs_key` = asks for a key and is not the server this skill started, or rejects the skill's key; `open` = answers with no key at all; `busy` = the port is taken but nothing answered in time), `managed_pid` (the server this skill started, accepted only while the process still has the start time recorded with its pid), `hardware` (chip, RAM, free disk), `model` (`downloaded` for the default or the `--model` you pass: true only when every weight file has the length its own header declares and no other repo filled the folder, `conflict` says why not), `default_model`, `remembered_models` (fraction, guard tier, tok/s, hardware, date, notes per model) and global `notes`.
2. **Install if `installed` is false:** `omlx_ctl.py install`. It takes the newest plain `vX.Y.Z` release, checks the sha256 against the one GitHub publishes, mounts the disk image, copies the new app next to the old one (`/Applications/oMLX.app.new`), requires Apple's notarization to check out, and only then swaps it in, keeping the old copy until the swap worked (`--force` on an installed app; it refuses while the skill's server runs). If the check fails nothing is installed and an existing app is untouched. No sudo. If the disk has under 4 GiB free or the Mac is not Apple Silicon on macOS 15+, say so and stop.
3. **Ask what to run**, unless the user already named a model (an `owner/repo`, or a name that matches one in `reference/models.md` or `remembered_models`; a description such as "uncensored" is not a name, so offer the default). Read `reference/models.md` before recommending any model. Use AskUserQuestion with the default first and labelled `(Recommended)`: `default_model` from the status (the model used last; on a first run `froggeric/Qwen3.6-35B-A3B-Uncensored-Heretic-MLX-4bit`). Add up to two candidates from `reference/models.md` that suit this RAM, and an Other for any Hugging Face `owner/repo`. One line per option: size, whether it needs offload, and the remembered tok/s when there is one.
4. **Recommend the configuration.** `propose_config.py <owner/repo>` works before the download (it reads the config and the first 256 KiB of each safetensors file, which holds the header, not the weights). Run `omlx_ctl.py status --model <owner/repo>` once the user has picked, so `downloaded` and the remembered settings are those of that model, and pass `--context <the remembered context>` to the proposal when there is one (it defaults to 32768). Read the model's card (README) for the required system prompt, thinking switch and sampling per mode; fetch it with WebFetch or `curl -sL https://huggingface.co/<owner/repo>/raw/main/README.md` (works before the download). Tell the user, briefly: resident or offload at what fraction, how many GiB stay in RAM, the memory guard tier, the biggest risk, and what is remembered for this model. If the plan is `too_big` or `too_big_even_offloaded`, say what would fit (see `reference/models.md`) and go back to step 3; do not invent a setting.
5. **Download if `model.downloaded` is false:** `fetch_model.py <owner/repo>`, in the background (25 MB/s was seen once, so the default model's 19 GB is ~14 minutes; do not poll, you are notified). It pins one commit and resumes when re-run. Every LFS file (the weights) is checked against the sha256 Hugging Face publishes and every other file against its git blob id. A file name that would leave the model folder is refused, a leftover `*.safetensors` from another revision is reported as `STALE` (delete it by hand: every `*.safetensors` in the folder gets loaded), and `.omlx-source.json` records which repo filled the folder, so a second repo with the same name is refused. The folder is marked unfinished until every file verified and no stale shard is left, and `start` refuses an unfinished folder; nothing is ever deleted for you. Say the size first (the proposal prints it). Public, ungated repos only.
6. **Start:** `omlx_ctl.py start --model <owner/repo> --system-prompt "<the card's required system prompt, with its thinking-off tag if it has one>"`, in the background (you are notified when it ends; do not poll): it takes minutes (server start, load, three timed chats) and can outlast a foreground tool timeout. If it was cut off, run `status` before retrying; `server: busy` means a server is still loading, so wait. It plans the settings, creates the API key if missing (`~/.omlx/api_key`, mode 600; an existing key file that others can read is made private), starts the server detached so it outlives this session, logs in to the admin API, applies the per-model settings (switching `mtp_enabled` off first when it plans offload and the model has it on), loads the model, retries with the `aggressive` guard and then smaller resident fractions when the load is refused for lack of RAM, proves the offload from the log lines this load wrote, runs three timed short chats and saves what worked. `--system-prompt` is used only for those test chats; oMLX keeps no per-model system prompt, and a card without a required prompt means leaving the flag out. Thinking is switched off in the test chats because at a few tok/s it is much slower; tell the user how the card switches it on. `start` reuses the remembered fraction, guard tier and context; pass `--fraction`, `--tier` or `--context` only to change them. It exits non-zero with the reason when it cannot, and then stops a server that this run started (a server it reused is left running). If the final message says other apps hold the RAM, tell the user which large apps are open (`ps -axo rss,comm | sort -rn | head`; `ps` shows an app's resident memory only, so oMLX's own wired weights show up in `top`, not there) and let them close them; never close apps yourself.
7. **Hand over** in the user's language, without printing the key:
   - **Chat:** `http://127.0.0.1:8000/admin/chat`, a link. The user logs in with the key; the page has a System Prompt field where the model card's system prompt goes (the browser keeps it).
   - **Key:** `file:///Users/<user>/.omlx/api_key` as a link, plus `! pbcopy < ~/.omlx/api_key` to copy it without showing it.
   - **API** for other clients: `http://127.0.0.1:8000/v1`, key from the same file, model id = the directory name.
   - The offload line and memory from the output, the speed series, and that the first request after a start can be slower. Thinking mode at a few tok/s is much slower than the same question with thinking off (an expectation, not measured).
   - It keeps running after this session; `omlx_ctl.py stop` stops it (`--force` kills it if the shutdown hangs).
   - Offer to open the chat in the browser (`open <url>`); do not open it unasked.
8. **Remember.** `start` already saves model, fraction, guard tier, loaded GB and last tok/s to `~/.omlx/skill-state.json`, and the next run proposes that model first and starts with those settings. Save lessons with `omlx_ctl.py remember --model <owner/repo> --note "..."` (for example "needs aggressive with a browser open", "refused: not MoE") and general ones about kinds of models without `--model`. `remember` only appends a dated note; nothing reads it but you, through `status`. When you learn that a model type does or does not suit oMLX offload, add the note.

If `server` is `needs_key` or `open`, something else owns port 8000; ask the user before touching it. If it is `busy`: with `managed_pid` set, a server this skill started is still loading, so wait; with `managed_pid` null, run `status` again every 30 s for about two minutes, and if it is still `busy` tell the user that something unknown holds port 8000 (`lsof -nP -iTCP:8000`) and ask before touching it (`stop` only ever signals a server this skill recorded). If it is `ours`, `start` reuses it: it sends the plan's concurrency and cache settings, applies the memory guard and this model's settings and (re)loads the model. The answer lists which settings applied live; on 0.7.0 only the memory guard did, and the rest take effect when the server is next started.

## What `start` rests on (verified on oMLX 0.7.0, macOS 15.5, M3 16 GB, 2026-10-17)

- `/admin/api/*` is 401 without a key; a Bearer key was rejected there on 0.7.0, so the script logs in with `POST /admin/api/login` and keeps the session cookie. `/v1/*` takes the Bearer key. Never turn on "Disable all authentication" to get around a 401, never print the key, and never put it on a command line (`--api-key`, `curl -H "Authorization: Bearer ..."`: visible in `ps`). The scripts read it from `~/.omlx/api_key` (or `$OMLX_API_KEY`) and send it over HTTP from inside the process; the server gets it through its environment.
- A load can be refused with HTTP 500 "does not fit under the dynamic memory ceiling" (seen on this Mac) or HTTP 507 (documented upstream, never seen here); the script treats both as a refusal and nothing else. Other apps hold the RAM. The attempts, in order: planned guard tier, `aggressive`, then smaller resident fractions under `aggressive`.
- Offload is proven only by the log line `moe expert offload: wrapped N layers at P% residency` among the lines written since this load began; an older line proves nothing. When the model was already loaded with the same settings no new line appears: `start` then says so, shows the last line and accepts it only if the server's own settings show offload at that fraction. Otherwise the model may have loaded fully resident.
- The three timed chats are 64-token answers with the prefill included, so they read lower than a long answer would (3.9, 3.8, 3.9 tok/s at 25% resident; 5.7 and 5.9 for 115 and 131 tokens). The first request after a fresh server start was slower (1.8 tok/s, then about 4). Report the series, not one number.
- A server whose shutdown hangs can keep its wired Metal memory (seen once: 8.5 GiB wired until the process was killed with SIGKILL). If a load is refused right after stopping a server, look for a leftover oMLX process (`ps -axo pid,command | grep -i omlx`).
- The key goes only to the process this skill recorded (or a child of it): `start` and `status` check with `lsof` who listens on port 8000 before they send it, so an unrecorded server there is `needs_key` even if it would accept the key. The pid record is written when the server is spawned, so `stop` still finds a server whose `start` was killed, and `start` removes it again when the run fails.
- `stop` signals only the pid it recorded when it spawned the server, and only while that process still has the recorded start time, so a pid the OS has reused for another program is never touched. `stop --force` sends SIGKILL after 20 s. `start` and `stop` take a lock, so two of them never run at once.

## Propose a configuration

    python3 -I ${CLAUDE_SKILL_DIR}/scripts/propose_config.py <model-dir | owner/repo> [--tier safe|balanced|aggressive] [--context 32768] [--json]

The argument is a local model directory or a Hugging Face repo id (only the config and the first 256 KiB of each safetensors file, enough for its header, are fetched; the weights are not). The report gives: the memory budget for weights, the plan (`resident`, `offload` at a fraction, or does not fit), per-model and global settings, the `omlx serve` flags, the equivalent admin-API calls, and warnings. Useful flags: `--ram-gb N` to answer "what if I had N GB"; `--metal-limit-gb N` when the exact Metal limit is known; `--json` to post-process.

- **Read the model card.** The script takes sampling from `generation_config.json`, but cards often recommend other values per mode and some require a fixed system prompt. oMLX has no per-model system prompt, so it goes in the chat page's System Prompt field or in the client's request.
- **Check what is flagged as estimated.** `Metal working-set limit ... (estimate)` means mlx was not importable; the budget can be off by a GiB or more (a guess, not measured). The transient allowance (1.5 GiB) and the 95% safety factor are heuristics, not oMLX constants; the load attempts and the sweep settle them. `--context` only sizes the KV term: a larger window leaves less for the weights in the plan.
- `propose_config.py` itself changes nothing. Never run `sudo sysctl iogpu.wired_limit_mb=...`; it is only ever suggested as text.

## Check that it worked

- `GET /admin/api/models` must show `"moe_expert_offload_supported": true` for the model, otherwise the toggle does nothing. An ineligible layer is skipped with a logged reason and the model then runs fully resident. `start` and the sweep read this flag themselves and stop when it is false.
- Qwen3.5/3.6/3.8 need oMLX's native kernels: use the official `.dmg` (this skill's install does); `brew install jundot/omlx/omlx --with-custom-kernel` needs full Xcode, and without the kernels these families silently run on much slower paths.
- A refused load (HTTP 500 "dynamic memory ceiling", or 507) means oMLX's admission estimate does not fit the memory ceiling: lower the fraction, or move the tier from `balanced` to `aggressive`; `start` does both by itself.
- Do not verify offload by diffing outputs across fractions: capacity changes reduction order, so greedy outputs can fork mid-answer while staying semantically exact.

## Measure instead of guessing

    python3 -I ${CLAUDE_SKILL_DIR}/scripts/sweep_offload.py --model-id <dir-name> --fractions 0.375,0.25,0.1875 [--prompt-file f] [--apply-best]

It sets the offload fraction through the admin API, reloads the model, warms up, measures TTFT, decode tok/s and (where the log has it; oMLX 0.7.0 logs none, so `n/a`) the expert-cache hit rate from the log lines written during the measured runs, then restores the original settings (or keeps the best with `--apply-best`). The best is the highest decode tok/s; `--objective ttft` ranks by time to first token instead. It reloads the model once per fraction, which takes minutes and ties up the server, so **ask before running it** (tuning is outside the consent of steps 2 to 6) and run it in the background. Use the fractions from the proposal's `sweep_fractions` (18.8% means 0.1875), plus the remembered fraction when it is not among them; `--model-id` is the part of `owner/repo` after the slash. Pass a realistic long prompt for agent/coding use: with offload, TTFT (prefill) is the pain point. It reads the key from `$OMLX_API_KEY`, else from `~/.omlx/api_key` (there is no `--api-key` flag) and refuses to run while `mtp_enabled` is on for the model. A final settings call that fails is reported, not hidden. A load the server refuses ends the sweep and restores the original settings. `--apply-best` leaves the winner set in oMLX, but the next `start` applies the remembered fraction again: to keep the winner run `omlx_ctl.py start --fraction <winner>` (it saves the fraction) and `remember` the numbers as a note. If the sweep refuses because `mtp_enabled` is on, run `start` once: it switches `mtp_enabled` off when it plans offload.

## Rules that are easy to get wrong

- Only **MoE** models can be offloaded, and only checkpoints that are MLX-quantized and in a supported family. A dense model that does not fit needs a smaller or lower-bit build; say so instead of inventing a setting.
- Offload cannot be combined with DFlash or VLM MTP, nor with `mtp_enabled` except for `deepseek_v41`, `glm5_next`, `qwen4_exp`. For every other offloadable family, `qwen3_5_moe` (Qwen3.5/3.6) included, it is MTP **or** offload; oMLX rejects the combination. A settings PUT changes only the fields it names, so `start` switches `mtp_enabled` off when it plans offload (and `moe_expert_offload_enabled` off when it plans resident) if the model has the other one on. The proposal turns MTP on only for a resident model with an MTP head in the `qwen3_5`, `qwen3_6` or `deepseek_v4*` families.
- More resident experts means fewer SSD reads, but a fraction that leaves little headroom is worse: macOS then compresses oMLX's memory and a request can hit the hard memory watermark. Measured on this 16 GB Mac with normal apps open, one run each and not a controlled sweep: 25% decoded at 3.9 tok/s, had 2.5 GB of oMLX's memory compressed and once aborted a request; 18.75%, 12% and 10% decoded at about 6 to 7.6 tok/s, differences inside the noise (the table is in `reference/memory-and-offload.md`). So treat the proposal's fraction as a ceiling: when the Mac is busy start one step lower and measure. The step lower is what `start --fraction` and the proposal's `sweep_fractions` offer. The proposal's ladder is a search grid; 12% and 10% were tried by hand.
- Concurrent requests share one expert cache and one SSD, so keep `max_concurrent_requests` low (the proposal uses 2) when offloading.
- `GET/POST /admin/api/models/{id}/settings/optimal` sends the chip, memory and model name to omlx.ai to fetch community benchmarks. Ask before using it.
- Never bind `--host 0.0.0.0` without a key (oMLX refuses anyway).
- oMLX moves fast (dev and rc builds roughly weekly). The setting names here come from its main branch on 2026-10-17 (release 0.7.0 stable, 0.7.1rc1 newest); when a call returns 422 or an unknown field, re-read `reference/settings.md` against the live `GET /openapi.json` before concluding anything.

## Reference

Read a file only when the step needs it:

- `reference/models.md`: before recommending or choosing a model (step 3): what makes a model good for oMLX and expert offload, candidate models with what was and was not verified, how to find more.
- `reference/settings.md`: when a call returns 422 or an unknown field, or you need a flag, a setting name or an admin-API endpoint: CLI flags, global and per-model setting names, endpoints, files and logs.
- `reference/memory-and-offload.md`: when a load is refused, the user asks why a fraction or guard was chosen, or before changing the fraction: guard tiers, the dynamic ceiling, how the budget is computed, offload mechanics, measured numbers with their hardware, what is verified and what is not.

Tests: `npm run test:omlx` from the plugin repository, or `python3 -B -W ignore::ResourceWarning -m unittest discover -s skills/omlx/scripts -p 'test_*.py'`.
