# Source map and a worked example

## Source map

| Layer | Source | Why it matters for tuning |
| --- | --- | --- |
| SDK launcher and QEMU engine | [AOSP `platform/external/qemu`, `emu-main-dev`](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-main-dev/) and its [development guide](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-main-dev/android/docs/DEVELOPMENT.md) | `android/emulator/` launches `qemu-system-<arch>`. QEMU presents the virtual CPU and devices; the platform hypervisor can run guest instructions directly when the architecture matches. |
| AVD options and launch-time hardware | [`android/emu/avd/`](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-main-dev/android/emu/avd/) and [`android-qemu2-glue/main.cpp`](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-main-dev/android-qemu2-glue/main.cpp) | The glue generates `hardware-qemu.ini` and passes the effective vCPU count and guest RAM to the engine. Look up `genHwIniFile` and the construction of `-smp` and `-m`. |
| Graphics | [`emugl_config.cpp`](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-main-dev/android/android-ui/modules/aemu-gl-init/src/android/opengl/emugl_config.cpp) and [Gfxstream](https://android.googlesource.com/platform/hardware/google/gfxstream/+/refs/heads/main/) | Guest graphics commands can be handled by a host GPU backend or software rendering. `auto` is a choice, not a renderer; GLES and Vulkan can have different backends. Inspect both when working on graphics compatibility. |
| Snapshot and UI | [`android/android-emu/`](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-main-dev/android/android-emu/), [`android/android-ui/`](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-main-dev/android/android-ui/) and [Studio's embedded emulator client](https://android.googlesource.com/platform/tools/adt/idea/+/refs/heads/studio-main/streaming/src/com/android/tools/idea/streaming/emulator/) | QEMU and the emulator libraries run even when the Studio panel is hidden. The standalone Qt UI and Studio's embedded client are different presentation paths; compare them only when diagnosing display or input overhead. |
| Preview engine | [`emu-main-next-v11.0`](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-main-next-v11.0/) and [next-generation preview notes](https://developer.android.com/studio/releases/emulator#next-generation-android-emulator-preview) | Source for the newer QEMU engine; check eligibility and the active Studio channel before attributing behavior to it. |

For a source build, start from the [emulator manifest](https://android.googlesource.com/platform/manifest/+/refs/heads/emu-main-dev/default.xml) and the linked platform instructions in the [README](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-main-dev/README.md). The manifest fetches dependencies outside `external/qemu`. `emu-master-dev` appears in older guides; follow the current README and use the release/build matching the local package when investigating version-specific behavior.

## Observed example: Apple Silicon

Observed in one local audit on an M3 host with 16 GiB RAM:

- An ARM64 API 35 AVD requested `2G` with GPU disabled and mode `auto` in `config.ini`. The last generated hardware file showed `2560` MiB, four vCPUs and `lavapipe`; the recorded command did not force a GPU backend. On the same host, a second ARM64 AVD launched explicitly with `-gpu host` recorded `host`. A third AVD explicitly requested `swiftshader_indirect`, which was recorded as `swiftshader`. Editing its profile alone would not remove that launcher override; use the modern `software` option if automatic software selection is intentional.
- The API 35 profile had Quick Boot enabled, but `-no-snapshot-load` in its launcher forced a cold boot. The same launch used a custom `-dns-server`; that was a networking setting for the test workload, independent of the boot mode.
- The stable SDK package was updated from `37.1.11` to `37.3.10`. The latter's release notes include a macOS fix for severe lag from App Nap and process scheduling. One headless, read-only cold boot of the API 35 AVD with `-gpu host` reached `sys.boot_completed=1` and logged Gfxstream and Metal. This verified boot and the hardware path; it did not quantify a speedup.
