# Android Emulator Tuning

Answer in the user's language. This workflow works from any directory, including outside a project checkout. Treat the SDK emulator binary, the AVD's system image, and Android Studio as separate components. Use the project's app or build only when measuring that workload.

- **Source or architecture:** Read `${CLAUDE_SKILL_DIR}/reference/architecture.md`. Point to the layer the user asked about and identify the branch; a QEMU engine branch is not the source of Studio's Running Devices panel.
- **Performance or configuration:** Start with the audit below. Keep it read-only for explanation or advice; apply only the settings the user asks to change.
- **SDK emulator update:** Follow the update workflow below. For CLI setup, use `android-cli` if available. Use `android-profiler` for guest traces and `android-ui-step` for UI navigation when those are the actual task.

## Audit and tune

1. **Identify the SDK and host.** Use the SDK of the actual launcher: check SDK Manager for Studio, or `android info` and `ANDROID_HOME` for terminal or CI. For a Gradle project, `sdk.dir` in `local.properties` can identify its build SDK; confirm it matches the launcher before updating anything. Use the selected SDK's `emulator -version`, `emulator -accel-check`, `emulator -list-avds`, and `adb devices -l`. For VM acceleration, check that the image ABI is compatible with the host and that `-accel-check` finds a usable hypervisor (Hypervisor.Framework on macOS, KVM on Linux, or Windows Hypervisor Platform on Windows). For CPU/RAM questions, check the host's physical cores, RAM and memory pressure.
2. **Select the AVD and read its settings.** Use the AVD the user launches; for a running instance, `adb -s <serial> emu avd name` maps its serial to its AVD name. Follow `path` in that AVD's `.ini` pointer. Check the [emulator environment](https://developer.android.com/tools/variables#envar) for custom locations such as `ANDROID_AVD_HOME`; the usual default is `~/.android/avd`. Read `config.ini` for the requested image path/ABI, `hw.gpu.enabled`, `hw.gpu.mode`, vCPUs, RAM, display and `fastboot.*`. Read `hardware-qemu.ini` for the effective settings from the last launch and `emu-launch-params.txt` for relevant overrides (`-gpu`, `-no-snapshot*`, `-dns-server`, `-memory`). Report missing or stale runtime evidence as such. These last two files are generated; change the Device Manager settings or the command that launches the AVD. Keep DNS values private unless the user needs them.
3. **For slow UI, test the renderer first.** Check the current run's startup log as well as the effective mode. `lavapipe` and SwiftShader render in software and compete for CPU. If `auto` picked software, compare with `-gpu host` on the same AVD using the same launch mode and workload. If it works and helps, set **Device Manager → Edit → Additional Settings → Emulated Performance → Graphics → Hardware** (`hw.gpu.enabled=yes`, `hw.gpu.mode=host`), or update the launcher if it overrides the setting. For rendering defects or instability, revert to Automatic or use Software as a fallback. Host CPU acceleration alone doesn't prove hardware graphics is active. Shrink the *guest* resolution in a separate lightweight AVD only if display fidelity isn't part of the test; shrinking the host window doesn't change the guest resolution.
4. **For slow launches, check Quick Boot.** `-no-snapshot-load` forces a cold boot while allowing a later save; `-no-snapshot` disables both, overriding Quick Boot in the profile. For ordinary repeat launches enable Quick Boot, let a cold boot complete and close cleanly to create a snapshot, then verify the next launch restored it. Profile or emulator changes can invalidate snapshots; software rendering can make them unreliable. Preserve any cold-boot or networking flags the workload needs and compare launches under the same conditions.
5. **Tune CPU/RAM after checking the renderer and boot mode.** Compare a smaller vCPU allocation with the current one under the same host load (e.g. when Gradle and Studio run together). Guest vCPUs aren't dedicated host cores. Compare effective RAM, since the emulator may raise a configured value, and check host Memory Pressure and swap activity during the workload. Swap already in use is historical evidence, not proof of current pressure. Increase RAM only if guest memory pressure warrants it and the host has room. Prefer the same Android version, services and display for each comparison.
6. **Report evidence.** Separate startup time, UI smoothness, and host impact. Change one factor per comparison; say which mode ran, how many comparable runs were measured, and what remains unmeasured. See [graphics and VM acceleration](https://developer.android.com/studio/run/emulator-acceleration), [command-line options](https://developer.android.com/studio/run/emulator-commandline), and [Quick Boot snapshots](https://developer.android.com/studio/run/emulator-snapshots).

## Update the SDK emulator package

1. **Preflight.** Record the SDK path, emulator version/build, and running instances. The update affects every project using that SDK. Avoid replacing the package under a running emulator; ask before interrupting an existing session. Check the [release notes](https://developer.android.com/studio/releases/emulator) for fixes relevant to the user's symptom. Discover the current release from the SDK repository instead of pinning a version from an earlier session.
2. **Update just `emulator`.** With the resolved SDK, run `android --sdk="<sdk>" sdk update --no-downgrade emulator`. The default channel is stable. If the Android CLI is unavailable, use that SDK's `sdkmanager --sdk_root="<sdk>" --channel=0 emulator` after checking the available version, or **SDK Manager → SDK Tools → Android Emulator**. Leave system images, other SDK packages and AVD profiles alone.
3. **Verify installation and boot.** Rerun `-version`, `-accel-check`, and `-list-avds` from the same SDK. Use a disposable test AVD: any compatible device profile and system image can verify boot, with no APK or project checkout required. If one is unavailable, report installation separately and leave boot unverified. With permission to launch it, use the bundled smoke check on macOS or Linux:

   ```bash
   python3 "${CLAUDE_SKILL_DIR}/scripts/boot-check.py" --sdk "<sdk>" --avd "<avd>"
   ```

   It cold boots headless with `-read-only -no-snapshot`, waits for `sys.boot_completed=1`, and stops its own instance. Even with these flags the emulator can touch QCOW2 disk files, so use an AVD whose files may change. Add `--gpu host` when verifying hardware rendering too, or `--timeout <seconds>` for a slower boot. Headless can influence `auto` renderer selection; use the normal window or embedded launch for a UX comparison. On Windows, start the test AVD in Device Manager and verify `adb -s <serial> shell getprop sys.boot_completed` returns `1`; use **Cold Boot** if cold startup is what you need to verify. Report a blocked boot check as such and show the useful error lines if it fails.
