The main agent coordinates; a fresh reviewer subagent challenges every step of the plan, every new class or file it adds, and what the plan leaves out. The plan is the only thing this skill edits, and only the main agent may edit it.

## What to review

If `$ARGUMENTS` is not empty, the plan is the file at that path. Read it whole.

If `$ARGUMENTS` is empty, review nothing yet. Ask one question in one message, "What plan should I review?", with these choices, then stop and wait for the next prompt:
- the plan of this session (the plan file that plan mode named, under `~/.claude/plans/`, or, with none, the last plan proposed in the conversation)
- a file (its path)
- something else (text pasted into the conversation)

The main agent identifies the application checkout, the plan path or verbatim plan text, and the authoritative requirement. Take the requirement from the plan's own Context or Goal section, the issue or the branch name when available. If the requirement exists only in the conversation, quote only the owner's request and their decisions verbatim, marking each decision as an owner decision. Do not paraphrase, supply planning rationale, include rejected options, or ask for routine confirmation. If the requirement is unclear, ask the owner instead of guessing. Retain the exact requirement text sent to the reviewer for the report. Do not derive the numbered steps or the result list in the main agent.

## Where fixes go

The reviewer proposes exact plan replacements; it does not edit any file. Apply them verbatim in the main agent, in the order returned. For each edit use its step number or anchor to locate the exact old text; change it only where that text matches uniquely. Report an edit as not applied if the old text does not match, is ambiguous, or write permission is unavailable. Do not improvise a replacement or apply it to another file. If the plan is a file, edit only that file. If it exists only in the conversation, edit no file: assemble the revised plan in memory from the exact replacements and print it in full at the end. Never edit code, never run a build or tests, never start carrying the plan out, never stage or commit.

## Git history required

After the main agent identifies the plan and application checkout, use the shell (`Bash` in Claude Code) in the application checkout under review. Write each Git command as one plain command that starts with `git log` (or `git show` where stated below), with no `$VAR`, `;`, `&&` or pipe; the shell's output is not a terminal, so Git starts no pager. Run `git log -1 --format='%H %cI' HEAD` before starting the helpers. Check that this is the history of the intended application, not an unrelated parent checkout. Use only read-only Git inspection; do not fetch, switch branches, stage, commit, build or run tests. If shell or Git access is missing or denied, or there is no readable committed history for the application, report the blocker, ask for access or a checkout with history, and stop before Part A without editing the plan. Do not substitute file order or modification times for Git history.

## Agents before the review

Once per invocation, after intake and the Git history check, the main agent starts each helper listed under Agents before the review in one message, in parallel. Give each the plan path or verbatim text, the same requirement text, the checkout path, and only the paths or technologies relevant to its job. Do not give any helper the planning conversation, a main-agent step list, proposed verdicts, or an explanation of why the plan was written this way. Each helper reads the plan and identifies the material it needs for its own job; for example, the Precedents helper finds implementation decisions from the plan as written. Give each helper its role instructions, including the Git dating procedure for Precedents. Tell each not to edit any file or start another subagent; the skill cannot enforce this. Each returns text in its final message, not a file. Wait for every helper report before starting the reviewer. Reuse those reports without restarting the helpers on later passes. If delegation is unavailable, use the inline fallback under Each pass.

1. **Standards agent.** Find the files in this repository that define how its code is written, tested and reviewed, and report which of them bear on the plan. Look for:
   - instruction files: `AGENTS.md`, `CLAUDE.md`, `.claude/`, `.cursor/rules`, `.github/copilot-instructions.md`, in the root and in the directories the plan touches;
   - contribution and design documents: `CONTRIBUTING*`, `docs/` (architecture, style, ADRs, earlier plans), the README sections on conventions, the PR template;
   - configuration that enforces a standard: `.editorconfig`, linter and formatter configs, test configuration, CI workflows.
   It reads headings first and only the sections that bear on the plan; it does not read a large file whole. It returns the list of files found, one line each on what the file governs, then the rules that bear on the plan, each as path:line and a short quote. If it finds none, it says so and lists what it looked for.
2. **Practices agent.** Search the web for what the technologies the plan names recommend. Follow "Web lookup" below: primary sources only, generic terms, neutral questions ("what does the official documentation recommend for X?", not "is Z correct?"). If the plan names nothing external, say so and do not search. It returns a list of practice, version or context, URL, short quote (or "unverified").
3. **Precedents agent.** For each implementation decision in the plan, search the application for code with the same responsibility and comparable constraints, including outside the target module. Compare how the application models, reads, parses, validates and exposes equivalent data, or handles the corresponding design question. Search for abstractions the plan may have bypassed, not just files or symbols it names. Read the implementations and their wiring. Date them by the commits that introduced the implementations, using the procedure below. Return the step and decision, the candidates and why they are comparable, the source `file:line`, the introducing commit hash and date, and which candidate is newest. If none match, report what you searched. If the helper cannot read history, return the candidate paths and the blocker so the main reviewer can check them.

**Dating a precedent.** Identify the line range of the relevant implementation at `HEAD`; use `git show HEAD:<path>` if the working-tree line numbers differ. Run `git log --no-ext-diff --no-textconv --format='%H %ct %cI' -L '<first>,<last>:<path>' HEAD` with the actual range and repository-relative path. Follow the patches back to the commit that adds the implementation for that responsibility. Confirm that the patch adds the implementation, rather than merely editing it, adding its enclosing file earlier, or moving it. Do not use `-1` or select the oldest displayed commit without reading its patch. Rank candidates by the introducing commit's committer timestamp (`%ct`); cite its hash and ISO date (`%cI`). The most recently introduced comparable implementation is the precedent; one is enough.

Line history is not proof across every rename or move. If it stops at a rename, use `git log --no-ext-diff --no-textconv --follow -p --format='%H %ct %cI' HEAD -- <path>` on the single path and check the earlier path. If the code moved between files, inspect candidate old and new paths with `git log --no-ext-diff --no-textconv -p --format='%H %ct %cI' -G '<distinctive-declaration-regex>' HEAD -- <old-path> <new-path>`; verify the additions and removals and trace the predecessor if one exists. Rename detection is heuristic; line history does not reliably trace cross-file moves, and a search by declaration can miss a renamed symbol. Squashed or shallow history cannot recover a hidden introduction order. If the introduction or ranking needed for a decision remains unverified, or equally recent comparable implementations disagree, report the evidence gap and ask before rewriting that decision. Never treat a known move or shallow boundary as an introduction.

4. **Architecture/Layers agent.** Identify the application's layers relevant to the plan from written architecture or dependency rules and from how the code actually works. Inspect relevant module and package responsibilities, interfaces, imports and calls, adapters, implementations and wiring. Use the project's own names and boundaries, not a fixed layer list. A folder is a lead, not proof; a module may contain several layers, and a layer may span modules. Return the relevant layers and what each owns, the actual consumer and provider at each relevant boundary, and candidate mappings from proposals in the plan to those layers, all with `file:line`. Separate the written architecture from code that does not follow it. If no distinct layers can be established, say what you read and why the evidence does not establish them. Do not decide alignment or fix the plan.

The helpers' output is context, not evidence. Before giving a verdict, read the applicable written rules and the candidate implementation files and wiring needed for the comparison yourself. Confirm the selected precedent's comparability and introduction from `git log`, including competing candidates when their ranking matters. If a lead does not hold or a later pass introduces a decision the helpers did not cover, search and verify the history yourself. If no comparable implementation is found, report where you looked and do not claim code alignment without evidence. Cite the source `file:line` you read and cite the introducing commit separately. Cite web sources by URL.

A rule in the project's own files that a step breaks is a finding ("not aligned"). If an applicable written standard and code disagree, the written standard wins. If two standards files contradict each other, ask the user which one wins. If written standards are silent on the decision, use the most recently introduced comparable implementation as the standard even if standards files exist for other topics. A deviation from that precedent is "not aligned"; apply "After a fix", including its owner-approval exception. A web practice that contradicts the project standard is an observation; it does not trigger a fix by itself. If no standards files were found, say so in the report.

## Each pass

On each pass, map the proposals to the affected application layers before Part A. Then run Parts A, B and C on the same text of the plan and apply the fixes ("After a fix"). The next pass reviews the new text and updates the map without restarting the helpers.

### Who runs each pass

The main agent owns the pass loop. A pass reviews one version of the plan with Parts A, B and C, then the main agent applies the reviewer's replacements under Where fixes go. Only the reviewer makes the verdicts and writes the replacements on the independent path.

### Start a fresh reviewer

For each pass, the main agent uses `Agent` in Claude Code or `subagent` in OpenCode to start a fresh generic child on the platform's configured model. In Claude Code it must be a non-fork subagent: a fork inherits the whole conversation. Do not resume a child, fork the conversation, or ask the child to invoke this skill again. Start the brief with `Independent review pass: review the current plan.` Give it the current plan verbatim and the plan path if there is one, the requirement text, the application checkout and relevant paths, the owner's answers and approvals so far quoted verbatim and marked as owner decisions, and each helper report verbatim. Include the applicable review instructions from this skill. Do not send the parent conversation, its reasoning, rejected options, earlier reviewer reports, or a parent-produced summary of the helper reports. Do not use the review brief opening in helper prompts.

Tell the reviewer not to edit any file, run a build or tests, ask the owner, or start any subagent. These are instructions, not a sandbox. The reviewer's first job is to list the plan's steps in order, one numbered line each, then list the results the requirement asks for, one line each: what must be true or observable when the plan is done. Use the same lists throughout the pass. If you cannot number the steps or name the requirement, give the main agent an exact question to ask rather than guessing. Work from the supplied inputs and repository evidence. Treat the helper reports as leads, not evidence. For each verdict read the relevant `file:line` yourself and cite it; verify precedent history and cite web evidence as required by the existing rules. Check the current plan, not what an earlier reviewer might have found.

The reviewer returns Markdown in its final message with these fixed headings, in order:

- `## Review report`: the report specified below, including its existing Parts A and B tables and Part C list. Give the verdict and cited evidence for each finding. Describe proposed actions as proposed, not applied. If the review cannot start because the plan cannot be numbered, a requirement cannot be established, or another prerequisite is blocked, identify the blocker instead of fabricating verdicts or table rows.
- `## Proposed plan edits`: for each replacement in order, give the step number or anchor, exact old text and exact new text. Use an empty new text for a deletion; anchor an insertion with unchanged text that is included in the replacement. Return `None` if there are no edits.
- `## Questions for the owner`: give each question in the exact wording the main agent should ask, with the affected step or decision and the evidence. This includes ordinary place questions, repository-backed departure approvals, and missing requirement or verification decisions. Return `None` if there are no questions. Do not invent an answer or propose changing a choice whose answer is still needed.

Wait for the reviewer's final result from the Agent tool or the OpenCode `<subagent>` report. Relay only the reviewer's questions to the owner, without answering them yourself. Use the owner's own words on the next fresh pass and label what decision they answer; do not carry the previous reviewer's verdicts or reasoning into the brief. When nobody can answer, finish the independent checks and replacements that do not depend on the answer, leave the affected choice unchanged, and list the question as open. Preserve the existing rules for decisions that forbid approval.

### Inline fallback

If delegation is absent or denied, run the entire review and each helper job in the main agent. If the reviewer fails to return a usable review, start one fresh reviewer once more for the same pass with the same inputs. An empty or partial result without the verdicts or report tables is not usable; an explicit prerequisite blocker with its owner question is usable even without table rows. Do not apply replacements from an unusable result. If the retry also fails, run the entire review inline, helper jobs included. Do not ask for permission to use this fallback or call it independent. Do not use the fallback to bypass the Git history requirement or any tool or file permission.

### Map proposals to application layers

Use the Architecture/Layers report as a lead. Read the applicable rules and the ownership and boundary evidence yourself before relying on the map. Where written architecture and code disagree, the written architecture governs what is allowed; show the difference and use the actual code to assess what a change would affect. Do not infer that a policy is followed merely because it is documented.

Keep the numbered steps. Within each step, identify distinct implementation choices the plan proposes or relies on and link each to every layer it changes or depends on changing. Include any layer or mapper required by the governing written rule or verified comparable path even when the original proposal bypasses it. If the Part A comparison reveals such a layer that was missed, add it to the map and check it before giving the layer verdict. Use the actual consumer or caller as the side above and the actual provider or dependency as the side below, even if an interface or injection reverses the source import direction. Check the immediate consumer and provider boundaries. If a contract change necessarily affects another layer, add that layer to the proposal's map and check it too. Stop following a branch at an unchanged contract. For a one-layer plan in a layered application, check that layer and its relevant immediate boundaries only; do not review unrelated layers. A proposal that changes no application implementation or contract still gets the ordinary step review, not a layer analysis.

If no distinct application layers can be established from the rules and code, ask the owner this once per review: "I could not establish distinct application layers from the project. Which layer boundaries should this review check, or should I treat the application as a single layer for this plan?" On the independent path, the reviewer returns this question and the main agent asks it. Use the answer before giving a layer verdict, and keep it for later passes without asking again. If the owner names boundaries, investigate them under the same evidence rules. If the owner confirms a single layer, review that layer and record that there is no distinct cross-layer boundary to check; do not skip the in-layer comparison. An answer does not substitute for a rule or code evidence.

If the reply arrives after the reviewer returns, resume the pending layer check once on the current plan with the owner's answer. On the independent path, the main agent starts a fresh reviewer with the usual inputs and the answer quoted verbatim, scoped to the layer-dependent checks in Parts A, B and C; do not resume the previous child or resend its findings. Use the usual report, replacement and question headings for the affected checks. When running inline, complete those checks inline. If no reply can be obtained, put the question and what you searched in the report, mark the layer check as blocked, and continue only checks and plan fixes that do not depend on the answer. Do not invent layers, silently skip the blocked check, or report it as passed. For a specific unverified boundary in an otherwise identifiable architecture, use the existing open-questions check if the missing evidence affects the decision.

### Part A: every step

For each step, answer six questions with evidence, not with a bare yes or no:
- **Why** do we do this step? Name the requirement it serves. If you cannot name one, the answer is "no reason".
- **Is it strictly necessary?** Would the goal still be met if the step were removed or smaller? Extra, cosmetic or speculative steps fail.
- **Is it aligned with the project standard?** For each implementation decision in the step, compare what the plan would do with the applicable written rule or, when there is none, the most recently introduced verified comparable implementation. Compare the design, including data shape, parsing and validation, ownership, reuse and tests as relevant. Check whether the step bypasses or omits a model, helper or other abstraction used for the same job, even if the plan adds no class or file. For example, if comparable HTTP configs use model classes and a shared deserializer, flag a step that instead round-trips a JSON object through manual string parsing and name the model and deserializer pattern it should follow. Cite `file:line`, say what differs and why the comparison applies, and give the verdict for each material decision. If the step proposes no implementation decision, say "not applicable".
- **Does it hold?** Every file, function, class, API, version and command the step names: does it exist and behave as the step assumes? Read it and cite `file:line`. For a step that creates something: is the path free, and does the neighbouring code have the shape the step expects?
- **Is it in the right place?** Compare the proposed file, class, module or layer with where the project puts similar work. Cite `file:line`. A violation of an established layer boundary is an alignment finding, not a place question. For other placement findings, say where the work should go and why in two plain sentences; do not change the proposed location without the owner's agreement.
- **Is it the most optimal solution?** Name at least one alternative you considered (an existing helper or class, a platform or library API already in the project, a shorter or simpler shape) and say why the step is better or worse than it. If the alternative is better, the answer is "not optimal".

For each affected layer, work through every proposal mapped to it and record the findings against its step. Keep the six step answers; do not repeat unrelated questions for every layer. For each proposal at each affected layer, check:

- **What already exists here?** Find the model, class, helper or pattern that serves the same responsibility. For an implementation decision within a layer, compare an implementation of that responsibility within the same layer, even if it lives in another module. To check ownership, look at the layer that actually does the job, not only where the plan proposes to put it. For a boundary decision, compare an equivalent handoff between corresponding provider and consumer layers, including what crosses and which side translates it. Use the written rule when one applies; otherwise select the most recently introduced verified comparable implementation for the applicable comparison, using "Dating a precedent". One verified precedent is enough per comparison. Use the Precedents agent's leads; if they do not cover the comparison, search the relevant code and verify its Git history yourself. Cite `file:line`. Distinguish an artifact that can be reused from a design to follow. If you found neither, say where you looked.
- **Does the proposal follow it?** State what the proposal reuses, follows or departs from. Compare responsibilities, data shape and mechanism against the applicable rule or precedent for this layer. Do not assume that similar types in different layers are interchangeable.
- **What happens at the boundaries?** Name the provider below and the consumer above, where they exist, and cite the contract on each affected side. Say what changes, what stays unchanged, and what cannot be verified. Check who owns any conversion and whether a type, error, dependency or behaviour changes across the boundary. If a side does not exist, say so. Record a shared boundary once and refer back to it from other proposals.

If the governing written rule or verified precedent establishes a layer boundary, moving a responsibility across it, bypassing a required layer or mapper, or passing a type across it contrary to that standard is "not aligned". Apply "After a fix", including the owner-approval exception for a repository-backed departure that no written rule forbids. A type crossing a boundary is not a finding by itself; show the governing rule or precedent that the proposed crossing breaks.

### Part B: every new class or file

A new class is any class, object, interface, enum, sealed type, composable, script or file the plan adds. List them with the step that adds them; if there are none, say so and go on.

Use the Part A map to identify each proposed class or file's owning layer. Check whether that layer already has something that can do the job, and whether the proposed type, dependency or interface fits its actual consumers and providers. For a bridge, name both sides and check which one owns the translation. Record the owning layer and relevant boundary evidence in the class row; refer back to evidence shared with Part A. Use Part A's alignment rule for established layer violations and the place-question rule for other placement findings. If no new class or file is proposed, Part A still checks whether the plan omits or bypasses one needed at a boundary.

For each, answer with evidence:
- **Is it correct as designed?** Behaviour for its callers, edge cases (null, empty, error, cancellation), lifecycle and threading, and the tests the plan gives it.
- **Is it strictly necessary?** Search the code for an existing class that could do the job; cite what you searched and found. Could it be smaller (speculative parameters) or be merged into its only caller?
- **Is it aligned with the project standard?** Use the same evidence and precedence rules as in Part A for this class or file. Compare its design and role, including data shape, dependencies, package, naming, injection and tests as relevant. Cite the applicable rule or comparable implementation at `file:line`.
- **Is it in the right place?** Same rule as in Part A.
- **Is there a more optimal variant?** Name the alternative design you considered and why this one is better or worse.

### Part C: what the plan leaves out

- **Coverage.** Go the other way round: every item of the requirement, and the step that serves it, or "no step".
- **Order and dependencies.** A step that uses something a later step creates, or that cannot be checked before a later one. Reconcile each changed boundary across steps: does the plan cover what the provider produces, what each affected consumer uses, and any required adapter or mapping, in a checkable order? An uncovered side, incompatible contract or missing transition is a gap. Do not require changes on the other side of an unchanged contract. Apply the same alignment and owner-approval rules to cross-layer gaps; do not use Part C to bypass an unresolved owner decision.
- **Verification.** For each step that changes behaviour, how it will be shown to work, and the test or check the project's own standards ask for. "Run the tests" without saying which is not a check. If a required result depends on a changed layer contract, name the check that demonstrates it. Reuse an existing criterion that demonstrates the result; do not require a test merely because a boundary was inspected. Every result the requirement asks for also needs an acceptance criterion in the plan; this holds for refactors, documentation and skills as well. A criterion states:
  - the **scenario**: the input and the conditions that matter;
  - the **observable result**: what is inspected (an interface, an API response, CLI output, a stored state, a document, the behaviour of a skill);
  - the **acceptance condition**: what counts as pass and what as fail;
  - the **check and evidence**: the concrete procedure, and where or how its output is inspected.
  - **Shape:** one compact line, adapted to the plan: "Criterion — result / steps: in situation X we observe Y; passes if Z. Check: method. Evidence: artefact or output. Status: planned, not run, or blocked by a decision."
  - **Proportion:** a criterion follows the requirement, not the number of files; one criterion may cover several steps, and a criterion that is already good stays as it is. A yes/no condition is measurable: do not force percentages or scores. "Visible" means inspectable: do not ask for screenshots when there is nothing to look at. Cover the error cases and limits the requirement names, and no more.
  - **Comparative gains** (speed, size, memory): name the baseline, the conditions, the sample and a justified threshold. A measurement nobody has taken becomes a measuring step; a threshold that is a product decision becomes a question for the user. Never invent a value.
  - **Planned, not run:** this review does not run the plan's checks and does not show that the plan works. Mark every criterion "planned, not run", never "passes" or "verified".
- **Hard to undo.** Steps that delete, overwrite, migrate, push, publish or release. Mark each one as needing the user's go-ahead in the plan.
- **Unevidenced assumptions and open questions.** What the plan takes for granted without a `file:line`, or leaves undecided. Ask the user instead of guessing.

### After a fix

An unsupported departure from an applicable code precedent is "not aligned": reshape the affected plan text to match the precedent even if no written rule covers the decision. If the plan gives a repository-backed reason to depart and no written rule forbids it, ask the owner to approve the departure before keeping it. Show the proposed choice, precedent and reason; mark the decision as blocked and do not rewrite or approve that decision while waiting. If the owner approves, record the exception in the plan and re-review it without asking again for the same approved choice. If the owner rejects it, reshape the plan to match the precedent and re-review it. This exception does not override a written rule or the separate "Place questions" agreement requirement.

Fix an established layer violation in the plan: put the work in the governing layer, restore the required intermediate layer or mapper, or use the contract type that belongs at the boundary. Add a plan step only if the requirement needs it to restore that contract. This is an alignment fix, not a place question. If the owner-approval exception applies, leave that decision blocked while waiting. These changes affect only the plan; never move or edit application code during the review.

If any answer is "not optimal", "no reason", "not correct", "not aligned" or "does not hold", or Part C finds a gap, fix the plan text: remove or shrink the step, reshape it to match the standard, correct the false assumption, add the missing step. A result with no criterion, or a criterion that lacks a part, is a gap: add or repair the criterion in the plan, from the requirement and the neighbouring tests. Keep the plan's structure and touch only what the finding concerns. Do not add steps for improvements nobody asked for. If the fix needs a decision about the requirement or the scope (a threshold, an expected behaviour), stop and ask instead of guessing; the report lists that criterion as blocked. After the edit, re-read the plan and check the step numbers and the cross-references.

## Place questions

Ordinary "Right place" findings do not change the plan by themselves. At the end, ask the owner about them in one list: what the work is, where the plan puts it, where it should go and why. Change that proposed location only if the owner agrees, then run one more pass. Do not put an established layer violation in this list: fix it as "not aligned", or ask for approval of a repository-backed departure under "After a fix" when that exception applies. Never move application code during a plan review.

## Web lookup

Search the web only when you are not sure about a fact the answer depends on (API behaviour, deprecation, recommended pattern), and the repo does not settle it. Use primary sources only: official documentation, release notes and source of the library in question. Do not use blogs, forums or AI summaries as evidence. Cite the URL in the report. If no reliable source is found, say the point is unverified and do not base a fix on it. Search with generic terms only; never put project code, internal names or secrets in a query.

## Stop

Stop when a full pass changes nothing, or after 3 passes (then list what is still open). Stopping is not approval: a plan whose essential criteria are still blocked by a decision is not approved, and the report says so.

An alignment decision blocked by missing history or pending owner approval remains open; stopping does not approve it.

The main agent counts review passes, not launch attempts. After an applied change, start the next fresh pass within the same limit. When an owner answer calls for a further pass under the question rules, give it to a fresh reviewer within that limit. Stop when a full pass changes nothing, or after 3 passes, as above; report unresolved questions and edits not applied. Preserve earlier reports for the user, not as inputs to a later reviewer. An unanswered decision is not approval.

If the owner answers the no-distinct-layers question, complete the pending layer check once with that answer even if the preceding pass changed nothing or was the last allowed full pass. This completes a deferred check, not another full pass; the limit on further full passes still applies. If the layer check remains blocked because the owner has not answered, report it as incomplete; do not approve the plan on that basis.

## Report

This section defines the reviewer's report for each pass. In a later pass, report what the current plan shows; do not reconstruct earlier findings. The main agent preserves the exact report text from each completed pass, labelled by pass, so that an earlier finding remains visible after the fix. The main agent relays each report verbatim: do not summarise, soften, drop or silently override a finding. Append only the mechanical status (pass, replacements applied or not applied, and fallback if used) and the reviewer's owner questions. Put any disagreement in a separate `Main agent note for the owner`; it does not change a verdict or replacement. If the requirement was taken from the conversation, show exactly what was handed over under `## Requirement given to the reviewer`. For a conversation-only plan, give the full revised plan as specified in Where fixes go.

If the full review falls back to the main agent, the first line of the user-facing report is `Not independently reviewed: <reason>. This review ran in the conversation that produced the plan.` Substitute the concrete failure or restriction for `<reason>` and then use the same report format.

Start with the standards files found (path and what each governs), or "none found". Then one table for Part A and one for Part B, one row per step or class, each answer in a few words with its `file:line`:

| step | layers / boundaries | why | necessary | aligned | holds | right place | optimal | action |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | UI only; contract with `AuthRepository` unchanged (`c.kt:8`) | login fix | yes | yes, like `b.kt:40` | yes, `a.kt:12` | yes | yes | none |
| 2 | not applicable | no reason | no | n/a | n/a | n/a | n/a | removed |
| 3 | data → domain → UI: plan formats the price in `PriceRepository`; the code formats it in the UI mapper (`d.kt:31`) | show discount | yes | not aligned: price formatting belongs in the UI mapper, like `d.kt:31` | yes, `e.kt:9` | see aligned | no | formatting moved to the UI mapper step |

Both tables have a `layers / boundaries` column immediately after the step or class. In the step row, use short proposal and layer labels to show each affected layer and the evidence-backed effect on the consumer or provider contract. Use the same labels in `aligned` for reuse, the applicable standard or precedent, and the verdict. In the class row, show the owning layer and any relevant boundary. Refer back to shared evidence.
